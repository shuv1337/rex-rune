# M2.8 — tab icon count (small second slice)

Implemented against `43bad823291354e63df088999ee632bae11f8063` (#72 tab fill).
Validated locally 2026-11-11 PST. This is not completion of the broader M2.8 work.

## Shipped behavior

Interface → Sidebar and tabs adds **Show tab icons**, a 0–5 stepper and one
compact, inert **Sample tab** preview. The preview uses the real program resolver
and icon-row renderer with five existing glyphs: terminal, Claude, Vim, Git and
Cargo. It demonstrates every count without a new page or placeholder controls.
Search discovers the actual row label through the existing Settings registry.

- `interface.tab_icon_count` defaults to **1** in new, old and partial files.
  Saved integer values above 5 (within the `u8` representation) normalize to 5;
  stepper presses saturate at 0 and 5. Existing settings error handling applies
  to malformed/non-`u8` JSON values. No existing key is migrated or renamed;
  `interface.tabs_fill_available_space` stays where #72 put it.
- **1 preserves the original semantics**, not simply the foreground process:
  resolve the focused pane (first server block if focus is absent/invalid), then
  use its deciding status record's `app`, else its cached foreground program.
  A deciding record without `app` falls back to foreground, not a lower-priority
  record's app. `TabActivity.program` and icons share that exact extracted code.
- **2–5** traverse that focused pane first, then the remaining panes in server
  layer/block order. Deduplicate by resolved glyph, not program spelling, then
  cap: `vim`/`nvim` share one, as do unknown programs and shells. Empty tabs and
  absent metadata retain the existing terminal fallback.
- Aggregate tab activity severity does **not** sort panes/icons. Within a pane,
  the legacy status-record resolver still decides which app represents it.
  Cached program/status changes replace that pane's resolved glyph in place;
  focus changes and deduplication can change the resulting distinct sequence.
- **0** appends no icon children and therefore no icon-to-label gap. Icons stay
  15 pt, 8 pt apart, in the tab's existing active/inactive monochrome ink.
  No new assets, mappings, colour modes, shell tiles, badges or theme gates.
  Sidebar icons now show the cached program name on hover, including at default
  count 1; previously only toolbar icons had that tooltip. For a truncated sidebar
  label, hover elsewhere on the row to see its full tab name instead.
- Toolbar and sidebar share the resolver and renderer. Tab labels, active/muted
  state, activity words, progress, menu targets and event handlers remain their
  existing surfaces. Fill mode reserves the **actual** icon count × 23 pt
  (glyph plus following gap), 40 pt of name and whole status/mute marks, with
  the existing 96 pt floor. Count 1 has the old floor exactly.
- Preference changes save locally and request selected-tab reveal, not host
  requests, ownership, input, split changes, pane movement or grid resize.
  There are no new actions, remote permissions, background tasks, process reads,
  server queries or polling. Existing host event caches are the only input.

## Limits and deferrals

At 640 pt the protected identity, chips, actions and 48 pt drag region can leave
less than one pill's width. Selected reveal still exposes its trailing portion;
with five icons and status the icons/name may be offscreen, and with Downloads
even a status word may be partly clipped. Arrows and visible-portion menu
interaction remain functional. Sidebar names can truncate to an ellipsis beside
five icons and a status word. This is not a responsive toolbar/sidebar redesign.

Native Wayland/compositor, IME, screen reader, fractional DPI and native
multi-client ownership/focus acceptance were not run. Native Downloads combined
with multi-icon overflow was not exercised; that combination is headless.
Native script coordinates are pinned to the private 1024×700 test window.

Colour and shell-theme icon modes, theme gating, focus-follows-mouse/Rune
workarounds and #44 move-to-new-tab are deferred/excluded. No updater files,
Settings → Updates, update tests/wiring or updater docs were changed; no
version, dependency, lockfile or vendored code changes. No push, PR, merge,
tag or release. Implementation is focused local recovery, not imported external
fork code; no new library/licensing material is involved.
