# M3.2 — conditional Activity toolbar chip

Implemented on ec0de79 (after #83). Verification: 2026-11-12, Pacific Standard Time.
This is a focused extension of the [Activity list](M3.2-activity-list.md), not full M3.2 parity.

## Shipped

- A button only while known, unmuted tabs **off screen** report OSC 7501 Blocked or Error.
  Blocked wins over Error; the count is tabs, not programs or panes. All blocked kinds count.
  The currently displayed host/session/window is excluded even when the native window is
  unfocused. Other tabs in that session still count.
- The connected-host, server-ordered session/window walk is shared with the Activity list
  in `Workspace::activity_tabs`. Only sessions in the host's session list with a cached
  layout can contribute. Muted tabs and disconnected hosts are omitted there.
  The chip additionally respects `notifications.show_in_tabs`; the list's existing
  ordering, filter, inclusion of the on-screen tab and unseen-Done behavior are unchanged.
  Sidebar session words are unchanged.
- Idle, Working, unseen Done, Bell and OSC 9;4 progress alone do not create a chip.
- Clicking opens the existing `client.activity` list. The first field accepts typing
  immediately; Escape restores terminal input. This is a button role with a full accessible
  label and an effective-keymap tooltip through `shortcut_help`.
- Model wakes drive appearance, count and disappearance. No timer, polling, status query,
  new action, setting or dependency. No host, terminal, ownership or size command is sent by
  drawing or opening it. Seeing the chip/list does not acknowledge a tab or close its notes.
- It is drawn only in the toolbar: always in Always mode, and in On hover and Hidden only
  while the toolbar is revealed or pinned. It is never floated over the terminal (see
  "Independent review and rework"). It does not reserve terminal space. The existing
  active-tab reveal key includes its presence, so the tab is revealed again when it
  comes or goes.
- One label at every width. It is not drawn below 720 pt of window width, and below
  1000 pt it waits for a pending key sequence or a download chip to leave. The download
  chip, the pending-sequence chip and the tab strip's arrows are exactly what they are on
  master in every case; `downloads_view.rs` differs from master by one `pub(super)`.

## Choices

1. **Words and colour:** `1 needs you` / `3 need you` in WARNING; `1 error` /
   `2 errors` in DANGER. Needs-you suppresses the error count, not the list's error rows.
2. **No short form.** The first draft shortened needs-you to `Need 3` below 1000 pt.
   It read like a demand for three things and saved about 20 pt, so the chip has one
   label everywhere and gives way instead (next item).
3. **Order and room:** pending sequence → Activity → Downloads, after the tab track.
   Identity, actions and the minimum 48 pt native drag space keep their room. Below
   1000 pt the chip is absent while a key sequence is pending or a download chip is
   showing: both are brief, and a waiting tab's chip returns when they leave. Below
   720 pt it is not drawn: measured at 640 pt, the tab strip is 110 pt wide at rest, 51 pt
   beside the download chip, and would be 24 pt beside this one.
4. *(Removed.)* The first draft also hid the tab strip's scroll arrows while both chips
   shared a narrow bar, and made the download chip compact with tabs in the sidebar.
   Neither remains.
5. **Motion:** no chip animation. The chip is never in the floating-status surface; in
   On hover and Hidden modes it rides inside the floating toolbar, which keeps its
   existing spring. Neither pane geometry nor terminal content animates.
6. **Focus:** unlike the download chip, the Activity press must not call `tx.blur()` after
   opening its text field. Native acceptance caught that doing so lost immediate typing
   despite the headless focus assertion passing. The final press calls `show_activity`
   directly, preserving the new field's focus.

## Coverage is deliberately incomplete

The chip knows exactly the cached inventory the Activity list knows. A session not opened
since connecting may contain a waiting tab whose status this client has never heard about.
**An absent chip is not a guarantee that nothing needs you.** README says this explicitly.
No prefetching or new subscriptions/queries were added.

Deferred: elapsed time, a by-session toggle/grouped count, prefetching other sessions'
status, and activity in/redesign of the identity chip. No always-present eye button.

## Independent review and rework

Cursor-pool Opus reviewed `c603596` and found the core sound (with no chip nothing
changes; the Activity list refactor keeps contents, order and targets; nothing is sent
and nothing is marked seen; pressing it is safe) but asked for two changes before merge
and answered three product questions. The parent reworked the chip accordingly:

- **It no longer floats.** In Hidden and On hover modes the first draft floated the chip
  over the top-left pane, as downloads and key sequences do. Those are brief; a tab can
  wait for hours, and an opaque patch that takes presses meant for the terminal conflicts
  with "the terminal is the content". The chip is now drawn only when the toolbar is.
- **The arrow-hiding rule is gone**, not narrowed. It triggered at any width under
  1000 pt, so a half-screen window lost its tab arrows whenever an agent waited during a
  download. The reviewer suggested measuring the track; the parent instead made the chip
  give way in narrow windows (Choices 3), which needs no measurement and leaves the
  download chip's code as it is on master.
- **No short form** (Choices 2), as the reviewer recommended.
- **Which tabs count** is unchanged, on the reviewer's recommendation: every tab except
  the one on screen. A count tied to what is visible would change with scrolling,
  overflow, window width and the sidebar, and switching sessions would change it with
  nothing happening. Put precisely, these are the tabs that would notify while you are
  looking at the window; the on-screen tab is excluded whether or not the window has
  focus, which is where this differs from the notification rule.

Docs follow the rework: DESIGN.md's Toolbar bullet opens with what the toolbar is again,
and no longer claims room "to reveal the active tab" at minimum width.

Final parent validation on the reworked code is in the PR description. The private
native acceptance was rerun (`native-uoulty7d/`; 1024 pt, toolbar always shown, no download, so the paths it
exercises are unchanged by the rework). The implementer's captures under
`evidence/branch/` predate the rework: their 640 pt images show a chip that is no longer
drawn at that width, and the `Need N` short form. The parent's captures are under
`~/.cache/agent-ws/chip-parent-captures/`.

Not done from the review's optional list: computing the summary once per frame, a
warning-colour pixel check for the native script's absence checks (they are OCR
negatives), preselecting the first off-screen row when the list opens from the chip, and
a 640 pt case with a long session name (moot now that the chip is absent there).

### Re-check

Cursor-pool Opus re-checked `1b6c43c`: with no chip the bar is exactly master's, the
chip never floats, every drawing site uses the conditional form, and the show rule

  with a test at 960 pt and 150%.

  regenerated captures and labels the first draft's.

Two test gaps it noted are closed: the chip arriving and leaving on its own while the
strip overflows (the reveal), and a download floating in Hidden mode without the
activity chip.

After these changes the parent reran formatting, the full suite (**962 passed, 0
failed, 6 ignored**), strict clippy, the release build and the private native acceptance
(`native-rh1__z23/`). The zoom test was shown failing against the window-width
