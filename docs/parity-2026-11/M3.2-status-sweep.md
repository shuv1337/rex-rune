# M3.2 — one status pass per connection

Base: `c940d94` (after #86). Implemented and checked 2026-11-12, Pacific Standard
Time. This closes the initial unopened-session gap shared by the Activity list,
sidebar session word and toolbar chip; it is not full M3.2 parity.

## Shipped and decisions

- `src/connection/status_sweep.rs` is the small status reader/inventory walker.
  `prefetch.rs` still owns detached layout reads. The host loop shares one slot
  **across both readers**, using the existing 25 ms pace and eight-second deadline.
  Waiting for a reply never waits in the host command/event handler. No new
  dependency, setting, subscription or timer for repeated status reads.
- Start only after bootstrap, attachment/selected-session restoration, existing
  size/theme restoration, selected status/title/process reads and keymap setup.
  Selected-session reads remain first. A short-lived connection that fails during
  this work never starts its background pass. Reconnect creates fresh attempt sets
  and drops old receivers; it does not enqueue another pass on the old connection.
- Walk the **current** server session vector in order. For each session, read its
  missing layout with `session.view`, then each terminal block's `program_status`.
  Already cached layouts are reused. New sessions and panes newly discovered in a
  cached background layout join once; there is no frozen startup-only queue.
- Status attempts are separate from selected-session title/process attempts. Mark
  the status attempt **before sending**, including failures. Selecting a swept
  session still gets its normal attach/title/process work, but not another status
  query. No background title/process reads, attachments, data tickets, creation,
  selection, resize, ownership, theme declarations or input from the sweep.
- Missing layouts, including those needed to place live block events, now go
  through the same detached layout reader rather than an awaited event-handler
  refresh. The sweep attempts each missing session layout once. The sidebar keeps
  its existing eligibility/backoff retries (1/5/30 seconds), after the initial
  pass. A failed sweep layout seeds that backoff even if sidebar eligibility
  arrives later. Successful views serve both callers. Collapsing the sidebar does
  not discard an in-flight read that also serves activity.
- Refusals/timeouts are quiet and not retried by the sweep. Failed status reads
  stay failed for the connection. Coverage is derived from the current inventory:
  a removed session/block does not leave a permanent failure warning; a layout
  recovered by the sidebar/navigation can complete coverage.
- `parse_status` produces `live: false`, using the same snapshot replacement
  semantics as the existing selected-session query. Cold queried Blocked/Error
  contribute their usual words/counts. **Queried Done is retained in the model but
  is not an unseen Done:** no notification/latch, no Done row/word/chip. This is the
  existing product rule, not a new Done display. Browsing marks nothing seen.
- Only two booleans reach the UI: reads in progress and incomplete coverage. No
  progress counter or new chrome. The Activity list says **Reading activity…**
  while work is in flight/queued; afterward **Some activity could not be read.**
  if needed; after a clean pass it has neither a line nor reserved space.
  **1 host is not connected.** / **N hosts are not connected.** remains first for
  down hosts. Reading takes precedence over failures until pending work settles.
- **No cap or lazy trigger:** measured local cost was light. The 40-session run's
  roughly nine seconds is deliberate pacing, not stalled input. A cap would keep
  the very coverage gap this work closes. No setting was justified.

## Measurements

Evidence root: `~/.cache/agent-ws/rex-m32-sweep/`. All servers, sockets, configuration,
HOME/XDG directories, session bus and displays were private. Rex API 13:
`rex 0.0.1794418166-g7b4cbc`, commit `7b4cbcbc6b67172a4c191ae243cd385b15578924`.

### Method

`scripts/status-sweep-private.py --bench 12` and `--bench 40` create five tabs per
session: three single-pane tabs, one two-pane tab and one three-pane tab (eight
terminals/session). Shells are idle `/bin/sh`; status responses are empty. This
measures inventory cost, not a simulation of hundreds of chatty coding agents.

`examples/status_sweep_probe.rs` runs the **production HostConnection worker**, with
its selected session but without visible terminal streams. It accepts only the
private sweep scratch Unix endpoint and never creates anything. A transparent Unix
WebSocket proxy records requests/responses and UTF-8 JSON byte lengths. Bytes below
exclude WebSocket/HTTP framing, socket overhead and terminal data. The worker reports
wall time from observed `connected` to `activity_reading == false` (1 ms sampling).
The proxy independently reports first background request to last response.

Every 100 ms during the pass and for five seconds afterward, the probe sends a
read-only selected-session `session.view` through the **same host command loop**.
That command's existing follow-up view refresh is included too. Proxy send-to-reply
RTTs measure both. These are not PTY echo, UI frame-time or WAN measurements.
The server's `/proc/<pid>/stat` user+system CPU is read at the first/last sweep
request/response, at 10 ms resolution, excluding shell child processes. An additional
CPU number covers the entire probe including the five-second rest comparison.

The selected session's existing eight status + eight title + eight process reads
are deliberately excluded from **sweep** totals. Thus all 96/320 terminals receive
a status read, but only 88/312 are background status reads. Snapshotting every
session view and every terminal's size/owner before/after the worker checks exact
read-only behavior; both session sets passed.

`a6c6dadc965bab010a8a4cbfc91fcb241c696a29f1f5cdc8abe4965d691a9752`.

`scripts/status-sweep-private.py --native` uses three private sessions, Xvfb/openbox,
private HOME/XDG and a private bus with the existing recording fake notification
service from `notification-quality-x11.py`. A real PTY program emits OSC 7501 Blocked
**once, before the client connects**, then sleeps. The client always selects Session-0;
Waiting is in never-opened Session-1. Rendered/OCR checks and captures show `1 needs
you`, the sidebar's `Needs approval`, and Waiting in the Activity list. The clean
list has no coverage warning. The fake service is running and records zero Notify

The proxy drops the client's sockets without stopping Rex, preserving the PTY and
its old status. After automatic reconnect the three surfaces show it again, without
another OSC report or visiting that session. This tests connection loss/recovery,
not server process/state restoration after a restart.

ordinary selected-session restore advances its view revision and resize declaration's
`updated_at`; actual sizes/owners and background views remain unchanged. Those
expected restore effects are not attributed to the sweep or erased from the raw
snapshot evidence.

## Parent validation and two things the first draft did not say

The parent reran formatting, the full suite and strict clippy on the cherry-picked
commit (971 passed, 0 failed, 6 ignored) and then made one change and recorded one
consequence. Final results, including the parent's own benchmark and native runs, are
in the PR description.

**A read no longer replaces a live report.** A background session's layout and its
status are read moments apart. A report that arrives live for a session the pass has
not reached yet is held until the layout places its tab; the status read that follows
then replaced the block's records with the server's answer marked as old. If the app
had not looked between the two, the tab first appeared with an old record and its
desktop notification was never sent. Before this slice there was no status read for
background sessions, so a live report always stayed live. `status_sweep::merge` now
keeps any record that arrived live on this connection and takes the rest from the
read; `a_read_replaces_old_records_but_never_a_live_report` covers it.

**Knowing every layout must not change Ctrl Tab.** Ctrl Tab and Ctrl Shift Tab stepped
through every tab of a session whose layout the client had, and treated a session it
had not loaded as one stop. With every layout read, every tab of every session would
have become a stop, and stepping onto a tab of a session the person had never opened
sends `session.focus_window`, changing that session's active tab on the server for
every client. The connection now records the sessions whose layout it holds only for
activity (`HostModel::background_views`: read in the background, never selected on
this connection), and `cycle_tab` keeps such a session one stop unless its tabs are
listed in the sidebar. Selecting a session takes it out of the set. DESIGN.md's rule
is reworded to match. One difference from before remains: a session known only from a
live event or from a sidebar listing that has since been closed is now one stop too,
where it used to be stepped tab by tab.

## Independent review and fixes

Cursor-pool Opus reviewed `4955e79`. Its run was reported as failed by the harness
after it had written its findings; they were read from its thread. Verdict: request
changes. It found the loop, the at-most-once bookkeeping, reconnect handling and "old
news stays old" sound, endorsed shipping without a cap, and required three changes,
all made:

1. **A status read could bring back a record the server had just removed.** A detached
   reply is handed to its receiver while the socket is read, and an event that arrives
   right behind it is handled first. A `program_status_removed` was then applied to
   nothing and the older read re-inserted the record, leaving a permanent Needs you or
   Error. The connection now notes the record ids removed live while a pane's read is
   out and drops them from the read. A loopback test that sends the reply and the
   removal in one flush failed 4 of 4 runs before and passed 6 of 6 after.
2. **A live report for a session the pass had not reached waited for the whole pass.**
   On master such an event triggered one layout read at once. Now it puts that session
   at the front of the pass: its layout is the next read, through the same single slot.
   A loopback test pins the order and that the report stays live.
3. **Ctrl Tab**, above. The reviewer also found the `session.focus_window` effect.

Also made from its notes: a layout that changes while its background read is out is read
once more (that change event had no layout to compare with); a status read that returns
nothing for a pane with nothing known no longer wakes the app (about 350 no-op wakes in
a 40-session pass); AGENTS.md lists the example.

### Slow links, measured after the review

The proxy can now hold every server-to-client frame (`--delay-ms`). One read is in
flight at a time, so the pass grows with reads × round trip. The measured times are
longer than that product: the probe's own comparison reads (two round trips each,
every eight delays) go through the same host loop and take about a quarter of its
time in the delayed runs:

| Injected delay | 12 sessions / 96 panes | 40 sessions / 320 panes |
| --- | ---: | ---: |
| none | 2.46 s | 8.76 s |
| 50 ms | 8.17 s | 25.0 s |
| 150 ms | 24.5 s | 74.9 s |

The read counts are the same in every run (99 and 351). A session a live report
arrives for jumps the queue, so what waits is only old state for sessions nothing is
happening in. Reading two to four panes at once on slow links would shorten this and
is left as a follow-up.

The first delayed runs found something else. The measuring probe sent a comparison
read every 100 ms, each awaited on the host loop for two round trips; at 50 ms that
kept the loop continuously busy, and **the pass sent nothing at all in 120 s**. The
background reader's wait is created afresh on every loop iteration and loses to a
command that is always ready. So background reads yield completely to commands: while
the loop is saturated they make no progress, and they resume when it is idle. The
sidebar prefetch has always behaved this way. For a person typing on a slow link that
is the right priority; the probe now spaces its reads at eight times the delay. The same
holds for the layout read a live report puts at the front: it also waits for the loop
to have a free turn.

## Three reads in flight (after #87)

The owner asked for the follow-up: allow three status reads in flight, as one
constant, with the same live-report priority and yielding.

- `status_sweep::IN_FLIGHT` is 3. It bounds the reads of this pass and of the sidebar
  prefetch together, layout reads included (server-info and directory reads are
  separate and not counted); at most one of them is a layout read, which still goes through the
  sidebar prefetch's single slot. Starts are still 25 ms apart, so the local pass is
  no faster: it was bound by pacing, not by waiting.
- The reader holds its reads in a list and returns the first to answer or to pass its
  own eight-second deadline. The wait is cancel-safe: a read is taken out only in the
  poll that returns it.
- The removal bookkeeping is now per pane (`ControlState::status_reading` maps each
  pane whose read is out to the record ids removed meanwhile), so a removal applies
  to its own pane's reply whatever order the replies come back in.
- Unchanged: a session a live report arrives for is read next; a read never replaces
  a live report; one read per pane and per session per connection; background reads
  still get no turn while the host loop is continuously busy.

Tests: `reads_finish_in_the_order_they_answer_and_each_once` (unit) and
`three_reads_are_out_at_once_never_four_and_a_removal_goes_to_its_own_pane`
(loopback: three unanswered reads, no fourth for 250 ms, a removal for the middle
pane, replies out of order, the fourth read going out while the first is still
unanswered). The refusal test no longer depends on a request arriving within the
25 ms pacing gap: it accepts the concurrent requests in whatever order they arrive.

Re-measured on a private server, parent's runs, same method as above:

| Added delay | 12 sessions / 96 panes: one in flight → three | 40 sessions / 320 panes: one → three |
| --- | ---: | ---: |
| none | 2.46 s → 2.46 s | 8.76 s → 8.76 s |
| 50 ms | 8.17 s → 5.29 s | 25.0 s → 14.6 s |
| 150 ms | 24.5 s → 11.9 s | 74.9 s → 28.7 s |

Read counts and bytes are identical to the single-flight runs (99 and 351 reads;
21,430 / 57,973 and 76,254 / 205,953 JSON bytes). Server CPU over the pass was
0.04–0.05 s and 0.17–0.24 s. Session views and every pane's size and owner were
unchanged in all six runs.

The speed-up is 1.5 to 2.6 times, not three. The likely reason is the order of the
work, not measured separately: a session's status reads cannot start until its layout
has come back, and the next session's layout is not asked for until the current
session's status reads have all started, so an eight-pane session takes about three
round trips where it took nine. Layout reads also stay one at a time. As above, the
probe's comparison reads share the loop in the delayed runs, so the seconds include
them; the one-versus-three comparison is like for like. Reading the next layout
earlier would help slow links further and is not done.

Not shown by these runs or the tests: whether a real server answers one connection's
requests one at a time. The test server answers out of order and the proxy delays
every frame equally, so neither can show three slow status reads holding up an
ordinary request on the server's side.


## Activity-row elapsed time (subsequent slice)

[Elapsed time](M3.2-elapsed-time.md) retains `updated_at` as a last-report baseline,
not a state-transition timestamp: private observation found it moves on same-state
message and progress updates too. Read-back rows explicitly say “reported”; later
same-state live reports preserve that earlier lower bound. This adds no requests or
changes to sweep concurrency, notification policy or coverage.

## Limits and remaining unknowns

- This is a sequence of best-effort reads, **not an atomic server snapshot**. There
  is no periodic reconciliation. Status changes whose events never reach this
  client can leave cached state stale; failed reads remain unknown. No new
  per-record event/query sequencing layer was added to the existing query semantics.
- Muted tabs, Activity in tabs, chip width/toolbar visibility rules and offline
  hosts still suppress display. An absent chip/word is not an unconditional all-clear.
  Bell and OSC 9;4 progress are not recovered by `program_status`.
- No WAN/SSH latency, silent-server large-inventory runtime, multiple-host native
  capture, Wayland, screen-reader or frame-statistics benchmark. One eight-second
  deadline per unanswered request bounds each wait, **not the whole pass**; a large
  slow server can take much longer while commands/events continue flowing.
- The native capture is 1024×700. Headless coverage checks exercise rendering, not
  a new 640×480 native capture. Existing size/display-rule tests still pass.
- No server-side CPU claim includes terminal child CPU. The benchmark's same-loop
  view RTT is a concrete control responsiveness check, not proof of PTY/render latency.

## Reproduction, failures and cleanup

Use one build directory and disk-backed short TMPDIR:

```sh
export CARGO_TARGET_DIR="$HOME/.cache/agent-ws/rex-m32-sweep/target"
export CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 CARGO_INCREMENTAL=0
export TMPDIR=/var/tmp
cargo fmt --all -- --check
cargo test --locked --all-features
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo build --locked --release --bin rex-linux
cargo build --locked --release --example status_sweep_probe
python3 scripts/status-sweep-private.py --bench 12
python3 scripts/status-sweep-private.py --bench 40
python3 scripts/status-sweep-private.py --native
```

`/var/tmp` was used from the start, avoiding the known six download-test failures
with long HOME-based TMPDIR paths; no download assertions were changed. No Cargo,
lockfile, vendor, version or released changelog changes. All private children are
stopped by PID; the build directory is removed after verification, retaining logs,
wire traces, snapshots, captures, timestamps and executable hashes as evidence.

Development failures were fixed, not hidden: old wire tests needed the newly required
background reads; an app fixture dropped a host and then incorrectly counted its
Shutdown command as a sweep effect; a timeout test initially sat before production
items and failed clippy. Native harness iterations initially emitted unsupported
JSON OSC syntax, then held too much proxy traffic, then compared ordinary reconnect
restore timestamps against the first connection. The final harness uses Rex's
key/value OSC syntax, gates only the sweep request, and checks exact per-pass snapshots
plus unchanged actual sizes/owners across reconnect. Earlier logs remain in the
same evidence root; none of those failures required relaxing production behavior.
