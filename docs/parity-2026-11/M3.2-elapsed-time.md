# M3.2 — elapsed time on Activity rows

Implemented against `origin/master` (`45940cef190deeb1b9a288db4477c31e47b4c314`)
on `parity/activity-elapsed`; verified on
2026-11-12 (PST). This is Activity-list presentation only, not full M3.2 parity.

## Meaning and choices

This section describes what shipped, including the changes made after review (listed
at the end of this record).

- **The client's own clock starts only for a state it watched begin.** That is a live
  report that changes the state of a record the client already held, or a first report
  from a pane whose status was already read on this connection
  (`HostModel::status_read`: every answered status read that was kept, including an
  empty one; cleared on reconnect). Such a row shows `now`, `4m`. A same-state report
  changes its message/progress/kind but **not** its start.
- **Any other first live report is not an observed start.** A program that reports
  before the status pass has read its pane may have been in that state for hours. It
  keeps the report's own `updated_at` as a **reported** age, or shows no time when the
  report has none. The same applies to a same-state report over a record with no time,
  and for the rest of the connection to a pane whose read failed or timed out.
- A queried record starts with the age of its parsed server `updated_at`, compared
  to the client's wall clock **once**, when received; subsequent age uses the
  monotonic clock. The observed server updates this timestamp on every accepted
  report, including same-state progress and message changes. It is **not a state
  transition time**. All read-back states with valid times are usable as lower
  bounds, but are visibly qualified: **`reported 4m`**, not just `4m`.
  In particular a Working job may have been running far longer. This also applies
  to a blocked program that repeats its request.
- A live report replacing the same record in the same state keeps the earlier
  baseline, including its “reported” qualification. Thus “reported” means the
  report used as the baseline, not necessarily the latest report now in the cache.
  A different state starts the client's clock.
- Multiple records/panes still fold to the existing highest-priority state. A tab's
  time is that of the oldest current record in that state, and **none when any record
  in that state has no known age**: one pane's exact-looking time does not stand for a
  tab whose other pane has been there for an unknown time. A presentation-only,
  host/tab/connection-epoch clock follows the folded state, even while the list is
  closed, so that returning to Working after a blocked sibling clears starts **now**,
  rather than reusing the Working pane's older start. That clock gives way to the
  records when they are younger: equal-state message and progress changes do not
  restart it, but a tab whose records left the state and returned between two model
  wakes shows the newer start, and a tab with Blocked panes at 40 and 2 minutes drops
  from `40m` to `2m` when the older one is answered. Queried states remain explicitly
  report-based; the initial query pass is not an atomic snapshot.
- A Done latch without a matching Done status record has no age. Queried Done
  still never creates a latch, notification or row by itself. Missing or malformed
  timestamps show no age. The clock/cache does not participate in notification
  decisions, Done/Bell receipts or sorting, and is reset on connection epoch changes.
- Clock disagreement is not estimated or corrected. A timestamp up to 60 seconds
  ahead of this client's clock counts as now; one further ahead shows **no time**,
  because a server whose clock runs ahead must not make an old request look fresh. A
  timestamp more than 365 days old shows no time. Within those bounds an ahead or
  behind server clock understates or overstates the initial age; no accuracy beyond
  the two clocks is claimed. No new server request was added.

## Display and refresh

The existing 44 pt row, title/place block, glyph, selection outline, groups and
chevron column are retained. A known time is an 11 pt MUTED second line **under the
existing trailing state word**, right-aligned to that word's original edge. The
visible units are `now` below 60 seconds, then whole `m`, `h`, `d`, rounded down.
No seconds, ticker, animation, sorting change, new setting or action. Read-back
labels add the word `reported` so their lower certainty is visible without hover.
Long titles still ellipsize before trailing information; no-time rows take exactly
the old code path, including the original vertically centered state word.

Rune permits separate `.label` and `.help`: e.g. “Observed waiting for 4 minutes”
and “Known working from a report 4 minutes ago; state may have begun earlier”.
The rendered text and label are checked; actual screen-reader speech is unverified.

The existing app poll uses `Tx::wake_after`, as notices do. An Activity panel owns
one deadline; at 60 seconds it requests a local redraw and a new 60-second wake.
Closing drops the deadline; other panels and no panel request no refresh. Rune can
still deliver one wake already scheduled before close, but it is a no-op for
Activity and schedules no next wake. This path does not track activity, query,
mark seen, send host/PTY commands, reveal the selection or scroll it. No thread or
busy loop. Other normal model/input redraws may also update a visible label.

## Limits and brief discrepancy

`src/app/server_page.rs` does **not** parse server timestamps: it deliberately
shows literal strings. There was no parser or existing direct time dependency to
reuse. A small dependency-free RFC 3339 parser lives beside the activity clock;
calendar fields and offsets are validated before arithmetic. Leap seconds produce no
time; `-00:00` (UTC, local offset unknown) is accepted since the review below. It accepts `Z`, signed
hour/minute offsets, fractional seconds (truncated to nanoseconds), and lowercase
t/z. It does not modify Server Settings' literal timestamp policy.

Not verified: Wayland, WAN/SSH or real clock skew, screen-reader speech, elapsed
labels across suspend/resume, named child status records, or native multi-host
navigation. The injected minute test establishes the timer behavior; native
acceptance checks real initial labels, not an unattended real-minute wait.
Impeccable reports the existing legacy PRODUCT.md schema; optional `init` is
separate work, not a reason to migrate product/design records in this slice.

## Review (Cursor-pool Opus, on `65a1f2c`) and what changed after it

The review asked for one change before merge and listed lower ones. “Meaning and
choices” above was rewritten to match; the verification sections in between record the
delegate's run before the review and are kept as they were.

1. **A first live report no longer starts an unqualified clock.** Before, any live
   report with no earlier record got `now` and later `40m`, labelled as observed. After
   a connect, a program that sent a progress tick before the status pass reached its
   pane was shown that way although it may have been working for hours, and the pass's
   honest read-back age was then discarded in favour of the live record. Now
   (`StatusRecord::observe_at`) the client's own clock starts only where it watched the
   state begin:
   - a live report that changes the state of a record the client already held; or
   - a first report for a pane whose status was already read on this connection
     (`HostModel::status_read`, filled by every answered status read, cleared on
     reconnect) and found without that record.

   Any other first report keeps its own `updated_at` as a **reported** age, or shows no
   time when it has none. A same-state report over a record with no age is treated the
   same way. So a pane the pass has not reached shows `reported …`; a program started
   while the client is connected and caught up shows `now`, `4m`.
2. **The tab's own clock gives way to its records when they are younger.** Model wakes
   coalesce, so a tab can leave a state and return to it between two of them; the tab
   then kept an age its record had restarted ("Needs you 40m" for a question asked
   seconds ago). The same-state case now takes the younger of the tab's clock and the
   records' age.
3. **An unknown age in the group means no time.** A tab with two panes in the same state,
   one with no known age, showed the other pane's exact-looking time. It now shows none.
4. **Clocks that disagree.** A report more than 60 seconds ahead of this client's clock
   now shows no time, where it showed `reported now`: a server whose clock runs ahead
   must not make an old request look fresh. A report older than 365 days shows no time.
5. The time on the highlighted row uses the same lighter ink as the place line beside
   it; it was dimmer than its neighbour.

New tests: `a_state_the_client_did_not_watch_begin_never_gets_an_observed_clock`,
`host_event_path_watches_a_first_report_only_for_a_pane_already_read`,
`a_tab_that_left_a_state_and_returned_between_wakes_shows_the_records_younger_time`,
`one_pane_with_an_unknown_age_keeps_its_tab_from_showing_a_siblings_time`,

After these changes: `cargo fmt --all -- --check`; `TMPDIR=/var/tmp cargo test --locked
--all-features` **1011 passed, 0 failed, 6 ignored**; strict clippy; release build; and
`scripts/activity-list-x11.py` passed again on a private server. Its capture, opened by

Stated limits, not fixed:

- **Suspend.** Ages advance on the monotonic clock, which stops while the machine
  sleeps. If the connection survives a suspend (a server on the same machine), every
  time shown is short by the length of the sleep until the next reconnect.
- The refresh deadline counts from when the list opened, so a label can be up to a
  minute behind its boundary (`now` shown at 1m59s).
- A first report between connecting and the pass reaching its pane reads `reported`,
  even when the client did in fact watch it begin. That interval is seconds on a local
  server and was measured at 15 to 30 seconds for 40 sessions on a slow link
  ([status sweep](M3.2-status-sweep.md)). A pane whose read failed or timed out stays
  `reported` for the whole connection.

A focused re-check of `0c708c3` found the code ready and this record out of step with
it; the record was corrected, and a reply that is thrown away (its pane no longer in
the session's layout) no longer counts as having read the pane. The refusal test now
asserts that an answered empty read marks its pane read and a refused read does not.
