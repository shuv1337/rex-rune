# M3.4 — optional activity sounds (partial)

Built on `1f5ce5a`; merged with `origin/master` at `db0ecc8` (#95) before review. The
last section says what changed after the delegate's run and after review. Verification: 2026-11-12, Pacific Standard Time.
Partial **d5-30 / d5-31** only, not the rest of M3.4.

## Shipped

- **Play sounds**, Settings → Notifications, is **off by default**. Old JSON loads
  with it off; `notifications.play_sounds` is omitted when false. Updating this
  terminal client must not make it start making noise.
- `activity.rs::track_activity` still makes the news/visibility decision.
  `notify_state` applies the existing event-kind and muted-tab decision once,
  then dispatches independent desktop and sound channels. A sound is asked for
  exactly where a notification would be posted, for Needs you, Error or Done. That
  includes a program that finishes by removing its status record. Working, records
  that are only read back (they are not news), program messages and terminal bells
  never request sound.
- The tab in front of a focused window stays quiet. With the window unfocused,
  that tab can notify too. No sound decision marks a tab seen, claims ownership,
  changes terminal content/layout, or sends input or a server request.
- Fixed freedesktop names: Needs you → `dialog-warning`, Error → `dialog-error`,
  Done → `complete`. No sound choices, volume slider or bundled audio.
- Sound is independent of the Desktop notifications switch and D-Bus health.
  The existing per-kind controls remain usable for sound when desktop delivery
  is off (Starts working still belongs only to desktop delivery).
- **Play** explicitly tests Done, even with Play sounds off. It is a Settings
  button, not a new registered action or shortcut. No remote allowed-set change.
- The helper next to the switch says what it does ("For tabs you aren't looking
  at, for the kinds switched on below.") until there is something to report: no
  player or sound files found, a failed attempt, a timeout or the worker unavailable.
  It is quiet helper text, not a warning chip/toast. A successful page check does
  not hide the last failed attempt; a successful attempt clears it. The switch
  stays usable when playback is unavailable. No automatic install or retry.

## Process rules and implementation

| Rule | Enforcement |
| --- | --- |
| No work on activity with the switch off | `activity.rs::notify_state` gates before `sound_request`; lazy `Sounds::request` starts no worker for Cancel. No lookup/spawn on disabled events. |
| No discovery/spawn/wait on UI or host loop | `sounds.rs::run` is a dedicated worker; UI requests only touch a small mutex-protected slot and bounded wake channel. Settings draw only reads `sound_health`. Both page-entry paths in `workspace.rs` request one Check. |
| Player order and theme files | `sounds/player.rs::select`: `canberra-gtk-play`, `pw-play`, `paplay`, searched on the absolute directories of the local PATH only (`search_path`; a relative entry such as `.` is never searched, so a program in the folder the app was started from cannot be run). Canberra gets `[-i, fixed-id]`; the others get one absolute `.oga` path under `sounds/freedesktop/stereo` in XDG_DATA_HOME then XDG_DATA_DIRS (standard defaults; relative XDG directories ignored). |
| No shell or remote command data | `Sound::id` is a three-case constant mapping; `Invocation` is made only by `select`. `System::spawn` uses `Command::new(...).args(...)`, null stdin/stdout/stderr and inherited local launch environment. No server/title/message/app text is accepted by the sound API. |
| No chorus or delayed queue | `sounds.rs::Gate` gathers for 100 ms, keeps just the highest severity (Needs you > Error > Done), and admits no further event until one second after that attempt begins. Events while busy/cooling down are dropped, not postponed. Stale gather slots older than a second are discarded. A bounded one-token wake channel is not a command queue. |
| At most one player | One worker owns the child; Gate stays busy through discovery, spawn, polling and reap. Explicit Play while busy is ignored rather than queued. Play supersedes pending event audio and remains Done even if more events arrive. |
| Timeout, kill and reap | `sounds/player.rs::attempt` polls the child, enforces three seconds, calls the child's own `kill` on timeout/shutdown/poll failure, and always `reap`s a spawned child, including non-zero exits. No process-name matching. |
| Exit cleanup, without waiting in the UI | Dropping `Sounds` signals stop and wakes the worker. `app/mod.rs::run` retains a `Shutdown` and calls `finish` after Rune's event loop ends, joining the worker after child kill/reap. Normal exit/re-exec cannot leave a player behind. |
| Failure isolation | Missing, spawn, exit and timeout failures update only the sound helper; no logs per event, toast, notification change, replay or fallback attempt after a failed spawn/play. The next explicit/event attempt discovers afresh. |

A 100 ms gather window deliberately trades a small response delay for choosing
one meaningful sound across nearby host updates. The rest of the one-second
interval is a drop window, not a delayed-play queue. This is client-wide, not per
host or tab. Play bypasses the event cooldown but never overlaps a player.

  message audio remain out of scope. No sound-name notification hint was added.

  push, PR or tag.

## After the delegate's run: parent changes and review

Parent changes before review:

- Only **absolute** `PATH` entries are searched for a player
  (`sounds/player.rs::search_path`). The first version resolved a relative entry
  against the current directory, which would run a `pw-play` lying in whatever folder
  the app was started from.
- The helper wording above.

Cursor-pool Opus review of `7fa13d4` asked for one change:

- **A program that finishes by removing its status record made no sound.** That is
  the usual way a program finishes. The tab is then left with no record, so nothing in
  it is marked live, and the first version asked for a live record before sounding;
  the desktop notification said "Done" and the sound stayed silent. The extra
  condition is gone: a sound follows the notification's own news decision. Within a
  connection a finish reaches the client only as a live event (a removal, or a report
  of Done or Idle), so this adds no sound for old news.
  `a_program_that_finishes_by_removing_its_record_is_heard_like_it_is_notified` fails
  without the change (`~/.cache/agent-ws/sounds-review-before.log`).

Also from the review:

- The nothing-found line now reads "No sound player or sound files were found on this
  computer.", since `pw-play` or `paplay` without the sound files is the same state.
- Exit waits at most two seconds for the worker (`Shutdown::finish`). Looking for a
  player touches every `PATH` and data directory, and one on a hung mount must not
  keep the process alive after its window closes.

After these changes: `cargo fmt --all -- --check`; `TMPDIR=/var/tmp cargo test --locked
--all-features` **1032 passed, 0 failed, 6 ignored**; strict clippy; release build; and
`scripts/activity-sounds-x11.py` passed again with fake players only.

Stated, not changed:

- Opening Settings → Notifications starts the worker and looks for a player even
  with the switch off, so the row can say when nothing was found. Activity with the
  switch off still starts nothing.
- If the first player found cannot play (for example `pw-play` with no PipeWire
  running), every sound fails and the next player is not tried. The failing player is
  started again for each eligible event, at most once a second.
- A sound already playing when the switch is turned off plays out (up to three
  seconds). The quiet second counts from when a sound starts.
- The tests drive the gate and the player through fakes; the real worker loop, its
  wake channel and the exit join are exercised only by the native script.
- The app's existing lavapipe descriptors (`/dev/udmabuf`, a memfd) are not
  close-on-exec and are inherited by a player, as by the app's other children.
- When two panes of a tab both report Done, the later one in layout order decides
  whether the tab's state counts as live for other purposes; with the change above
  this no longer affects the Done sound.
