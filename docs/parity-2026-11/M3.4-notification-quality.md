# M3.4 — notification quality and health (partial)

Base: `958b369` (after #77). Verification: 2026-11-12, Pacific Standard Time.
Only gap rows **d5-41** and **d5-42** are addressed; this is not the rest of M3.4.

## Shipped

- One local worker handles Send, Seen, Check and Test. A failed `Notify`, absent
  service or disconnected bus does not terminate it. Each command is consumed
  once; later notes/checks can reconnect. Failed notes are never replayed.
- Activity notes replace the previous **live activity** note for the same
  host/session/window using `replaces_id`. Different tabs, sessions and hosts
  remain separate. `NotificationClosed` forgets the id. Daemon ids are scoped by
  the bus GUID and service's unique owner, so restarting either cannot carry an
  old id into a new service. Calls/signals are pinned to that owner.
- Blocked (Needs you) and Error use urgency **2**; all other states, program
  messages and tests use **1**. Many desktops keep critical notifications visible
  until dismissed: that is intentional for a tab waiting on the user.
- At the same activity-tracking point that clears unseen Done/Bell, seeing a tab
  closes its live desktop notes. The close is asked for **once**, when a tab with
  a note sent since it was last seen comes on screen, not on every update of a
  visible tab. Notification activation also requests that close before following
  the existing navigation path; a second close request is inert, and a repeated
  action signal for one notification navigates once. Only ids returned to this
  client for that target can be closed.
- The worker remembers the newest **64** notifications for replacing, closing and
  clicking. Older ones are forgotten (left on the desktop, no longer closed by
  this client), so a daemon that never reports a close cannot grow the list.
- A daemon that answers with a refusal keeps the connection, so clicks and closes
  of earlier notifications still arrive; only a timeout or a lost connection
  reconnects. A refused `CloseNotification` (the daemon no longer has the id) is
  not treated as trouble.
- Settings → Notifications ends with a **Desktop service** section holding the
  **Notification service** and **Send test notification** rows, below the
  switches, indexed by the existing Settings search. Health is Not checked yet,
  Available, Not found, Unreachable, or Rejected (the service answered and
  refused). Opening/re-entering the page
  requests one worker-side check; no page render performs I/O. A positive check
  requires a `GetServerInformation` answer, not just a session bus connection.
  It is explicitly a **last check**, not continuous monitoring or a receipt.
- The button sends “Rex test notification” only on a press. It has no default
  action or target, cannot navigate or create anything, and reports sent/failed
  with a short reason. “Sent” means accepted by the service, not displayed by
  the desktop. Trouble chips say Not found, Unreachable, Rejected or Failed in
  WARNING. The page-open check runs even with desktop notifications off and, like
  any D-Bus call to the service name, may start an installed notification daemon
  through D-Bus activation.

## Decisions and boundaries

**Program messages stay unreplaced.** OSC 9/777 messages are separate deliberate
program communications; they neither replace one another nor the activity note.
They still close when their known tab is seen. A message with no resolved tab
cannot be attributed to an arbitrary tab. Test notifications are similarly
unreplaced but have no tab lifecycle or click action.

**Tests work with Desktop notifications off.** This answers whether the desktop
can receive a notification without changing the user's saved notification policy.
The section's one footnote says so. No additional preference or registered action
is introduced; existing settings files and the remote allowed set are unchanged.

**No polling or resend queue.** Connections/checks/calls run off the UI thread,
with a three-second bound per operation, not a background retry timer. Each later
command can check the current owner and reconnect. A close is attempted once per
seen tab: if the service does not answer, nothing is queued behind it by later
updates of that tab, and the next attempt comes only after another note is sent
for the tab and it is seen again. A daemon that hangs therefore costs one bounded
attempt per command, not one per host update. As with any D-Bus timeout, a daemon might have
accepted a note whose reply was lost; the client cannot safely replay it or invent
an id to close it. No extra race-handling subsystem was added.

The existing Settings shell, cards, chips, buttons, search and scrolling are used.
At 640×480 all text/controls stay within the page; lower status/program rows use
the normal scroll viewport. No status dots, subpages, settings shell redesign or
terminal rendering changes. The restart-failure notification function is unchanged.

**Actual worker bus-loss test:** the opt-in
`notification_worker_reconnects_after_a_private_bus_restart` starts the actual
`Notifier::spawn` worker and private bus/fake service without opening a native
window. It sends a note, terminates the service and bus, sends a note while the

`worker-bus.log` and `worker-bus-1794476393/calls.jsonl` show exactly the before/after
notes, both with replace id 0, and no replay of the lost note. To rerun, choose a
fresh absolute directory under the evidence root as `REX_M34_PRIVATE_BUS`, set
`DBUS_SESSION_BUS_ADDRESS=unix:path=$REX_M34_PRIVATE_BUS/bus`, and run:

```sh
cargo test --locked --all-features notification_worker_reconnects_after_a_private_bus_restart -- --ignored
```

**The whole app does not survive losing its session bus, and this slice is not
why.** An exploratory native fixture saw the GUI end with SIGTERM (exit -15) when
the private bus was torn down (`bus-native-diagnostic.log`, `native-ejkhp4ka/`,
`bus-restart-experiment.py`). The parent repeated it with the notification worker
never started (Settings unopened, no note sent; no `rex-notifications` thread):
the app still exited with SIGTERM. The process has GLib/GIO mapped with `gdbus`,
`gmain` and `dconf worker` threads (GIO modules for dconf and gvfs, loaded at
runtime, not by this code). GDBus ends its process with SIGTERM when its shared
session-bus connection closes, which is what the evidence matches. So bus loss
ends the app as it does other GLib-using desktop programs, independent of
notifications; the worker's own reconnect is what the opt-in test verifies.
Evidence: `parent-bus-sigterm.py` and `parent-sigterm-fivan0ff/result.json` under
the evidence root. No toolkit or vendor change was made for it.

Initial verification exposed and fixed zbus 6's wrapped FDO error classification
(ServiceUnknown/NameHasNoOwner must be Not found, not generic Unreachable).
The first full UI run also exposed the history test's fixed-scroll assumption.
Both failures were fixed; no assertions were removed or softened. Native OCR uses
one enlarged, inverted crop rather than retrying recognition until a match.

### Independent review and fixes

Cursor-pool Opus reviewed `2e47b04` and asked for changes. It confirmed id scoping
across daemon and bus restarts, replacement, urgency, the zbus error
classification, unchanged click/activation/mute behaviour and no server effects,
and found one blocker and two smaller defects. The parent fixed them:

- **Blocker: a hung daemon stalled later notes.** `Seen` was sent for the visible
  tab on every host update; with a live note and a daemon that owned the name but
  did not answer, each cost a three-second wait and they queued without bound
  ahead of later notes, checks and tests. `Seen` is now sent once per notified
  tab (see Shipped). A new test failed before (5 commands where 0 were expected)
  and passes after; failing log `~/.cache/agent-ws/notify-review-before.log`.
- **Unbounded remembered notifications.** The earlier cap had been dropped. It is
  restored at 64, oldest first, with a test.
- **A refused `Notify` dropped the connection.** It now keeps it; only timeouts
  and lost connections reconnect. The native run shows the worker continuing
  after a refusal and the next note replacing its predecessor; it does not show
  that the connection was kept (the fake does not record the caller's bus name,
  and the replacement id would match after a reconnect to the same daemon too).
  That part was checked by reading the code.

Also from the review: a refusal reads **Rejected**, not Unreachable, and a refused
close is not trouble; one navigation per clicked notification; the icon is decoded
once per worker, not per note; "Sending test…" is not overwritten by an unrelated
health update; a missing session bus says "Could not connect to the session bus";
the Desktop service section moved below the switches.

Final parent validation on the fixed code: formatting, full suite (**907 passed,
0 failed, 6 ignored**), strict clippy, release build, the opt-in private-bus worker
test, six isolated capture runs (12 images; three inspected) and the private X11
acceptance rerun with the release binary (`native-r51nokye/`: 6 accepted Notify,
1 refused, 2 closes; its test-button click point moved with the section). Logs:
`~/.cache/agent-ws/notify-parent-fixed-{tests,clippy,worker-bus}.log`,

Validation after these changes: formatting, full suite (**908 passed, 0 failed,
